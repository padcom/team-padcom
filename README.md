# padcom dev team

A team of long-running Claude Code sessions that work across interconnected repos. You lead it through Discord, by talking to one bot.

```
You (Discord) <-> lead -> architect   plans and cross-project contracts
                       -> developer   branches, code, PRs
                       -> reviewer    reviews PRs
                       -> qa          runs and verifies PRs
```

Each role is a `claude -p` session running as a systemd user service, with `roles/<role>` as its working directory. Sessions talk to each other over Claude Code's same-machine messaging. An idle session spends no usage.

## Setup

1. Create the bot in the [Discord Developer Portal](https://discord.com/developers/applications):
   - Under **Bot**, reset and copy the token, and enable **Message Content Intent**.
   - Under **OAuth2 > URL Generator**, select the `bot` scope with View Channels, Send Messages, Send Messages in Threads, Read Message History, Attach Files and Add Reactions. Open the URL to add the bot to your server.
2. Connect it. Add `bin` to your `PATH`, or call `bin/team` directly.

   ```sh
   team set-token     # hidden prompt, so the token stays out of Claude conversations
   team pair          # DM the bot, then /discord:access pair <code>
                      # then /discord:access policy allowlist, and exit
   ```

3. Add projects, install, and start:

   ```sh
   team add-project git@github.com:you/some-repo.git
   team check
   team install
   team start
   ```

Then message the bot. Describe how the projects relate in your first message, or edit `shared/projects.md`.

By default the services run while you are logged in. To keep them running after logout and across reboots, run `loginctl enable-linger $USER`.

## Daily use

| Command | Purpose |
| --- | --- |
| `team status` | Service state |
| `team logs <role>` | Follow one agent's activity |
| `team tail` | Follow all agents' activity, as `[role] HH:MM:SS message` |
| `team restart [role]` | Restart one agent or all. Sessions resume their conversation |
| `team stop [role]` | Stop one agent or all |
| `team add-project <url> [name]` | Clone another project for the team |

`shared/tasks.md` is the task board, `shared/projects.md` maps the projects, and `shared/decisions/` holds design plans.

## What agents can do

Sessions run in `dontAsk` mode, so anything not explicitly allowed is refused and the session never stalls on a prompt. Roles and permissions are set in two files, and the rules are generated by `lib/team.mjs`:

- `team.json`: what the team can do on any project. Roles, models, capabilities, the `gh-*` permission sets and generic test commands.
- `team-project.json` (optional): what only this project needs. The project list, extra permission and env sets such as `sitl`, and per-role `env`, `envSets`, `permissionSets` and `allow`.

The two files are merged: lists are appended, maps such as `permissionSets`, `envSets`, `roles` and `env` are merged key by key, and plain values such as `model` in `team-project.json` win. `team add-project` writes to `team-project.json`.

Write `${TEAM_ROOT}` for the directory that holds `team.json`, in rules and in `env` values, so the team works from any checkout path: `"Bash(${TEAM_ROOT}/bin/arducopter *)"`, or `"Edit(/${TEAM_ROOT}/shared/screenshots/**)"` (the extra `/` makes Claude Code read it as an absolute path). Agents also get `TEAM_ROOT` in their environment.

| Role | Edit | Git and GitHub |
| --- | --- | --- |
| lead | `shared/` | Merges verified PRs with `merge-pr`; manages issues, labels, PR comments and CI runs |
| architect | `shared/` | Read only (views PRs, issues, repos) |
| developer | Own worktrees | Commit, push `agent/*` branches, open, comment on and close PRs, manage CI runs |
| reviewer | Own worktrees | Manage issues, comment on and close PRs, manage CI runs |
| qa | Own worktrees | Manage issues, comment on and close PRs, manage CI runs, run tests |

You do the deploying and releasing. `git push` is denied outright. The only way to push is `bin/push-branch`, which accepts just the current `agent/*` branch and never forces.

`gh pr merge` is denied outright too. The lead merges with `bin/merge-pr <pr-url> <sha>`, after the reviewer and QA have both signed off on that commit. The script refuses unless the PR is an open, non-draft `agent/*` PR of a project in `team-project.json`, its head is exactly that commit, and every CI check is green. A PR with no checks is refused. Sign-off itself is the lead's judgement, because the team shares one GitHub identity and the script cannot verify it.

### Limits of these controls

- These rules are guardrails, not a sandbox. `developer` and `qa` run project test and build commands, which are arbitrary code with your user's access. Only add repos you trust, because a malicious repo or dependency can get past the rules.
- Agents use your `gh` and git credentials. **Turn on branch protection on default branches** and require status checks, so GitHub enforces the CI rule itself. Do not require approving reviews, since the shared identity cannot approve its own PRs and `merge-pr` would always fail.
- Anyone on the Discord allowlist can direct the team. Keep it to yourself.
- All agents share one GitHub identity, so the reviewer can comment but cannot formally approve.

To allow more, edit `team.json` or `team-project.json` and run `team restart`. Rules are layered:

- `testCommands`: commands for roles with the `tests` capability.
- Top-level `allow`: rules every role gets.
- `permissionSets`: named groups of rules. Every `gh` rule lives in a `gh-*` set (`gh-read`, `gh-pr`, `gh-pr-create`, `gh-issue`, `gh-label`, `gh-run`, `gh-workflow`), so a role without `gh-read` cannot even view PRs. A role uses sets with `"permissionSets": ["sitl", "gh-run"]`. An unknown set name stops startup with an error.
- A role's own `allow`: rules only that role gets, such as `"allow": ["Bash(make test*)"]`.

Duplicate rules across layers are removed. These layers only add to `allow`, so the deny rules above still win.

Environment variables are layered the same way, least specific first:

- Top-level `env`: variables every role gets.
- `envSets`: named groups of variables, such as `"sitl"` or `"llvm"`. A role uses them with `"envSets": ["sitl", "llvm"]`, and a later set overrides an earlier one. An unknown set name stops startup with an error.
- A role's own `env`: variables only that role gets, overriding everything above.

`PATH` is the exception: entries from every layer are joined, the most specific first, and placed after the team's `bin/` and before the inherited `PATH`.

## Good to know

- The Claude Pro plan's usage is shared by all agents and by your own Claude use, so heavy work will hit limits. All roles use Sonnet except QA on Haiku. Change `model` in `team.json`, or per project in `team-project.json`, if you upgrade.
- Discord channels are a Claude Code research preview, and the flags may change.
- The Discord plugin is disabled at user scope on purpose. Only the lead enables it, so that other Claude sessions do not connect to the same bot. Do not enable it globally.
- After a plugin server fails, Claude Code skips it for 15 minutes. If Discord cannot connect at startup, the lead restarts itself after 16 minutes.
- If you switch Node versions with fnm, run `team install` again, since the services record the Node path.
- Run `team install` from a terminal on your desktop, since the services record `DISPLAY` and `XAUTHORITY` for tests that open a window. Without a display, the CEF host fails with a message about user namespaces.
